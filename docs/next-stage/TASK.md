# MUMAKA（木马卡）下一阶段开发任务书

## 一、项目定位与本轮目标

请基于当前已经运行的 MUMAKA 项目继续开发，保留现有代码、评分引擎、数据库和历史记录，不要从零创建新应用。

**产品名称：MUMAKA / 木马卡**

**副标题：新乐评主义 / New Music Criticism**

现阶段的产品定位是：

一款面向个人音乐评论创作的专业工具，能够快速收集专辑信息、选择音乐风格、完成六维评分、管理历史作品，并生成评分卡。

目前不追求将其开发为完整的公开音乐媒体网站。

本轮开发分为三个部分：

1. 实现免费的、轻量化的专辑链接信息导入。
2. 优化整个应用的工作流程、功能结构与操作体验。
3. 保留现有评分卡设计及导出功能，为未来整合第三方编辑器预留接口。

本轮工作的重点是**实际可用性、操作效率和代码可维护性**，而不是增加更多功能或重新进行品牌视觉设计。

## 二、第一部分：专辑链接导入功能

### 2.1 取消对付费 Spotify API 的依赖

现有 Spotify 官方 API 和服务端代理代码可以保留，但不应成为基础功能的必需条件。

目前个人使用频率较低，不希望为搜索和获取专辑信息长期支付订阅费用。

请研究并实现一种不依赖付费 API 的轻量级专辑元数据采集方案，优先使用 Python。

核心操作应该是：

**粘贴专辑链接 → 获取专辑信息 → 确认或修改 → 创建作品 → 进入评分。**

不需要复杂的用户设置、爬虫参数或采集管理页面。

### 2.2 信息采集内容

用户提供一个可公开访问的专辑详情页链接后，程序尝试提取：

- 专辑名称
- 艺术家名称
- 专辑封面
- 发行日期或年份
- 曲目名称
- 曲目顺序
- 曲目时长（如可获取）
- 专辑类型：Album、EP、Single（如可获取）
- 音乐风格或标签（如可获取）
- 原始链接及数据来源

其中，**专辑名、艺术家、封面、发行年份和曲目列表**是优先需要实现的内容。

其他信息可按来源网站的实际情况选择性获取。

不得编造未能取得的数据。

### 2.3 支持的来源

第一阶段请优先研究公开可访问的音乐专辑页面，例如：

- Spotify 专辑公开网页
- 网易云音乐专辑页面
- QQ音乐专辑页面
- Bandcamp 专辑页面
- Apple Music 专辑公开网页

不要求第一版全部支持。

请先检查哪些来源能够可靠、合法地提取公开元数据，优先完成一至两个能够稳定运行的来源适配器，再采用模块化结构扩展。

对于 Spotify，尤其注意：官网公开页面不代表一定能够稳定抓取全部曲目信息。应以实际可取得的数据为准。

提取时优先采用网页本身公开提供的 JSON-LD、Open Graph 或其他可合法读取的结构化元数据。

不得绕过登录、付费墙、验证码、访问限制或反爬机制，也不得使用未经授权的私人接口。

某个网站无法取得资料时，应友好提示并允许用户继续手动填写。

### 2.4 技术方案

目前应用为 React + TypeScript，部署在 GitHub Pages。

GitHub Pages 无法运行 Python 服务端程序，也不能可靠地直接从浏览器请求任意第三方音乐网站。

因此，请先检查现有部署架构，再确定一种适合个人使用、无需持续付费的实现方式。

优先考虑：

**方案A：本地 Python 轻量服务**

- Python 负责获取并解析专辑网页。
- React 前端提供粘贴链接和导入按钮。
- Python 将提取结果转换为统一 JSON 数据格式。
- 前端读取结果后进入专辑信息确认页面。
- 提供简单的本地启动方式。
- 明确处理跨域、HTTPS页面访问本地服务等限制；不要假定 GitHub Pages 上的远程网页能无条件调用本地 Python。

**方案B：本地导入工具**

如果无法在当前部署环境中稳定实现一键采集，可以先实现 Python 命令行或小型本地工具，提取专辑信息并输出 JSON 文件，再由网页导入。

这一方案可以作为可靠的第一阶段交付，而不是强行开发需要持续运行的服务器。

请比较两种方案的实际操作成本，优先选择最简单、稳定、免费、便于长期维护的实现。

不要为了这项功能引入数据库服务器、复杂部署平台或持续付费服务。

### 2.5 前台操作

首页搜索区域附近增加一个清晰但不喧宾夺主的入口：

**通过链接添加**

点击后：

1. 粘贴专辑链接。
2. 点击「获取信息」。
3. 显示提取到的专辑封面、名称、艺术家、年份和曲目。
4. 用户确认或手动修改。
5. 点击「确认并继续」进入风格选择。

封面应尽量自动获取并保存为可持久使用的本地资源；若来源限制图片下载或使用，则明确提示并支持手动上传。

不要让用户填写复杂的采集选项。

数据来源和抓取详情可以作为后台记录，不需要在前台大量展示。

### 2.6 数据保护

导入不得直接覆盖已经存在的评分。

如果用户导入的是此前已经评分的专辑，应提示可能重复，并允许打开原记录或另建记录。

应保存原始来源链接、获取时间和必要的元数据来源信息。

若用户修改导入的信息，以用户最终确认的数据为准。

抓取失败不能造成页面卡死、已有数据丢失或评分流程中断。

## 三、第二部分：功能结构与操作流程优化

### 3.1 明确两种操作模式

请保留并完善两个核心入口：

**A. 快速评分**

适合日常完成一张专辑评价。

工作流程：

查找或添加专辑 → 确认基础信息 → 选择风格 → 六维评分 → 生成评分卡。

**B. 专业工作台**

适合对已有作品进行管理、编辑和比较。

工作台应提供更高自由度，但不需要展示底层计算代码和所有算法细节。

两个模式必须使用同一份数据库和评分引擎。

### 3.2 首页结构

首页应保留：

- MUMAKA 品牌名称及简洁副标题
- 专辑搜索
- 通过链接添加
- 手动添加
- 快速评分入口
- 专业工作台入口
- 最近编辑作品

不要重新增加大段产品介绍、宣传标语、技术说明或复杂的功能卡片。

但也不要极简到除了一个搜索框以外几乎没有可操作内容。

目标是一个简洁、清晰、具有专业工具气质的首页。

### 3.3 专辑资料与风格选择

当前已经具备的两级风格选择需要继续保留。

一级风格和二级风格分别支持：

- 点击展开选择
- 输入关键词搜索
- 自动匹配已有选项
- 依据风格树显示正确的上下级关系

不要恢复一次性列出数百个风格的大下拉菜单。

所有地区共用统一的风格树。

可保留中国音乐与其他地区的偏好选项，但仅影响常见风格的排序与推荐，不应产生两套独立的评分标准。

如果采集来源提供音乐风格或标签，可以显示「参考风格」，但不得直接假定外部标签与 MUMAKA 内部风格分类完全一致。

用户应当始终拥有最终选择权。

### 3.4 六维评分交互

保留当前六维五星控件：

- 一行五颗星
- 支持半星
- 支持鼠标、触摸、键盘
- 支持确有必要的 N/A
- 不强制填写评分理由
- 不设置最低字数限制

评分过程应当快速、直接。

底层的权重、精确计算和修正规则继续使用已有 V0.19 引擎。

**不得为了简化界面而简化、替换或修改评分数学逻辑。**

普通用户只需要看见自己给出的六维星级和最终分数。

### 3.5 创作来源修正

此前已经建立创作来源修正规则。

前台不应要求用户手动调整百分比。

对于普通原创专辑，默认使用正常规则。

对于涉及翻唱、传统曲目、旧作重录或原创与翻唱混合的作品，提供自然语言的简洁选项，由程序在后台映射到现有修正规则。

例如：

- 以新创作歌曲为主
- 原创与已有作品混合
- 以翻唱或已有作品为主
- 特殊情况

如有必要，允许用户在专业工作台中查看当前修正结果，但不要让调整权重成为日常步骤。

如果现有资料不足以自动判断具体修正档位，应明确提示需要确认，而不是自行推测。

### 3.6 多风格专辑与 EP

这是需要重点完善的操作。

对于普通单风格专辑，默认只显示一个主风格，不出现额外设置。

当用户选择「包含多种风格」时，再展开相关操作。

请研究并实现一种非常直观的操作方式：

- 普通专辑：只选择一个风格。
- 多风格专辑：可以增加第二个或更多风格。
- 用户可以按曲目分配风格，或在具备可信依据时设置各风格的曲目比例。
- 系统自动根据已确定的跨风格权重算法计算综合权重。

对于只有三首歌、每首风格不同的 EP，应当可以轻松逐曲设置，不需要用户理解权重合成公式。

对于曲目较多的专辑，也不应该强制逐曲填写大量信息。

如有合适的默认策略，可提供一键采用整张专辑主风格、批量修改曲目风格等功能。

如果使用曲目比例，需要明确区分曲目数量比例和实际使用的权重汇总依据，不得擅自改变原有数学规则。

尽量使用简洁的单选、分段选择、列表和必要的展开区域，而不是表格堆叠或技术参数。

### 3.7 专业工作台

专业工作台主要包含：

**作品库**

查看、搜索、编辑、复制、删除、排序已经建立的专辑。

**评分记录**

查看六维星级、总分、评分日期，重新编辑已有评分。

**数据管理**

JSON、CSV等必要的数据导入导出及备份。

**设置**

管理基本偏好、默认导出比例、数据备份等。

**卡片工具**

暂时调用现有评分卡生成器。

工作台允许有更丰富的功能，但请采用清晰的侧边栏和内容区，而不是在一个页面中同时显示所有操作。

不要恢复复杂的审核管理流程或冗长的内部规则说明。

### 3.8 操作体验

请特别优化以下问题：

- 页面步骤清晰，用户知道当前在哪里、下一步做什么。
- 支持返回上一步，已有输入不得丢失。
- 自动保存草稿。
- 已存在专辑支持直接继续编辑。
- 完成评分后能够直接生成卡片。
- 从评分卡返回修改星级后，卡片能够更新。
- 移动端操作不能依赖鼠标悬停。
- 不出现无意义的必填框、重复确认和冗长技术提示。
- 错误提示使用普通用户能理解的中文。

不需要以功能数量证明产品完整性，优先改善实际使用流程。

## 四、第三部分：评分卡暂时冻结

现有评分卡的视觉设计和导出能力暂时保留。

**本轮不再重新设计评分卡，不调整整体美术风格，也不开发新的复杂图片编辑器。**

原因是后续计划引入另一套独立开发的图片编辑器，并与 MUMAKA 整合。

因此本阶段只需要：

1. 保证当前评分卡仍然能够正常预览和导出。
2. 保留现有比例及 PNG 导出能力。
3. 确保专辑封面、标题、艺术家、总分、六维评分、玫瑰图及短评等信息可以稳定传递。
4. 整理一个独立的评分卡数据接口。
5. 将评分数据与具体图片模板的实现解耦。
6. 为未来接入其他编辑器预留清晰的组件入口与数据结构。

建议建立统一的 `ScoreCardData` 数据模型，但必须与当前实际数据结构兼容，不得破坏旧记录。

以后接入新编辑器时，应该能够直接读取已有专辑和评分数据，而不需要重新录入或重新计算。

**当前不要为未知的编辑器编造复杂插件体系或进行大规模架构重写。**

## 五、设计风格与界面限制

产品品牌继续使用：

**MUMAKA / 木马卡**

「新乐评主义」作为副标题或方法论名称。

整体视觉以成熟、简洁、专业的音乐媒体与创作工具为方向。

参考 Pitchfork 的编辑设计原则：清晰的字体层级、合理的空间比例、明确的信息结构、克制的装饰。

但本次不需要重新制定主题色，也不需要启动全面视觉改版。

重点改进组件的对齐、间距、操作状态、页面布局和信息层次。

不要随意新增渐变、卡通图标、彩色面板、装饰性标语或复杂动画。

请先检查现有项目结构、依赖及部署方式，再开始修改。
